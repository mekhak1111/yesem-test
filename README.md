# YesEm test project

One Flutter code base, three applications, five platforms.

| App | Runs on | Selected by |
| --- | --- | --- |
| YesEm Mobile | Android, iOS | any mobile device; no flavor (placeholder page for now) |
| YesEm Desktop | macOS, Windows, Linux | flavor `desktop` (also the default when nothing is given) |
| YesEm Pin Code Manager | macOS, Windows, Linux | flavor `pincode` |

`lib/main.dart` decides the role in this order: a `--yesem-role=…` command-line
argument, then the build flavor (`appFlavor`), then `--dart-define=YESEM_APP=…`,
then Desktop by default. Every build contains all roles.

## Flavors per platform

* **macOS**: real Xcode build configurations and schemes (`Debug-desktop`,
  `Debug-pincode`, …) generated by `tool/add_macos_flavors.py`. Product names
  and bundle ids differ per flavor (`YesEm Desktop.app`, `YesEm Pin Code Manager.app`).
* **Windows and Linux**: built-in flavor support arrived in **Flutter 3.47**
  ([Windows](https://docs.flutter.dev/deployment/flavors-windows),
  [Linux](https://docs.flutter.dev/deployment/flavors-linux)). With 3.47+ use
  `--flavor` exactly as on macOS; each flavor builds into its own directory and
  the native runners take the window title from `FLUTTER_APP_FLAVOR`
  (`windows/runner/CMakeLists.txt`, `linux/runner/CMakeLists.txt`). The
  executable stays `yesem[.exe]`.
* **Older SDKs on Windows and Linux** (anything before 3.47, e.g. a global
  3.44 install used without FVM): `flutter build windows` and `flutter build
  linux` have no `--flavor` option. Use `--dart-define=YESEM_APP=pincode` (or
  `desktop`) instead; the window is retitled from Dart through
  `window_manager`. With the pinned FVM SDK this path is not needed.

## Flutter version (FVM)

The project pins **Flutter 3.47.4** in `.fvmrc` through
[FVM](https://fvm.app), because Windows and Linux flavors need 3.47+. The
global Flutter install on your machine is left alone.

```sh
dart pub global activate fvm      # once per machine, if `fvm` is missing
fvm install                       # reads .fvmrc, downloads 3.47.4 on first use
fvm flutter --version             # Flutter 3.47.4
```

Prefix every command below with `fvm` (`fvm flutter run …`). IDEs use the
pinned SDK through `.fvm/flutter_sdk`: VS Code picks it up from
`.vscode/settings.json` (launch configurations for both flavors are in
`.vscode/launch.json`); in Android Studio set Settings → Languages &
Frameworks → Flutter → SDK path to that folder and add the flavor name to the
run configuration.

## Run it

macOS:

```sh
flutter build macos --debug --flavor pincode     # build the helper once
flutter run -d macos --flavor desktop            # run Desktop, click Sign
```

Windows and Linux with Flutter 3.47+ (same shape as macOS):

```sh
flutter build windows --debug --flavor pincode   # or: flutter build linux --debug --flavor pincode
flutter run -d windows --flavor desktop          # or: -d linux
```

Windows and Linux on older SDKs:

```sh
flutter run -d windows --dart-define=YESEM_APP=desktop     # or: -d linux
```

Without a separately built helper, Desktop on Windows and Linux starts **its own
executable** with `--yesem-role=pincode`, so the Sign flow works right after
`flutter run` with nothing else built. On macOS a missing helper is an error
with the searched paths, because there the helper is a distinct app bundle.

Other commands:

```sh
flutter run                                # Mobile placeholder on a phone/emulator
flutter run -d macos --flavor pincode      # helper alone, with hot reload
flutter test                               # unit + widget tests (hermetic)
flutter test test_e2e                      # macOS: launches the real built helper
tool/build_macos_installer.sh              # macOS: dist/macos/YesEm-<version>.pkg
tool/build_desktop_bundles.sh              # Linux: dist/linux/{desktop,pincode}
tool\build_desktop_bundles.ps1             # Windows: dist\windows\{desktop,pincode}
```

The bundle scripts build both roles (with `--flavor` on 3.47+, with the define
otherwise) and copy them into two sibling folders, renaming the executables to
`yesem-desktop` and `yesem-pincode` (`.exe` on Windows). Ship both folders
together.

## macOS installer

`tool/build_macos_installer.sh` produces `dist/macos/YesEm-<version>.pkg`, a
standard Installer package that puts both `YesEm Desktop.app` and
`YesEm Pin Code Manager.app` into `/Applications`, where Desktop finds the helper.

1. `flutter build macos --release --flavor desktop|pincode` (universal arm64 + x86_64).
2. Copy both bundles to `dist/macos/apps/` and sign them (Developer ID if given).
3. `pkgbuild`: one component package per app, installed to `/Applications`,
   marked non-relocatable. Otherwise Installer "updates" any other copy with the
   same bundle id, such as the one in `build/`, instead of installing.
4. `productbuild` with `tool/macos_installer/distribution.xml` (title, welcome and
   conclusion pages from `tool/macos_installer/resources/`, macOS ≥ 12) joins
   them into one installer.
5. Notarize and staple, if configured.

Without environment variables the apps keep Xcode's ad-hoc signature and the
package is unsigned. That's fine on the Mac that built it. Any other Mac rejects
a downloaded copy ("unidentified developer"). To distribute it, you need an Apple
Developer Program team with **Developer ID Application** and **Developer ID
Installer** certificates:

```sh
xcrun notarytool store-credentials yesem-notary --apple-id … --team-id … --password <app-specific>
APP_SIGN_IDENTITY="Developer ID Application: … (TEAMID)" \
PKG_SIGN_IDENTITY="Developer ID Installer: … (TEAMID)" \
NOTARY_PROFILE=yesem-notary tool/build_macos_installer.sh
```

Install from the command line with `sudo installer -pkg dist/macos/YesEm-0.1.0.pkg -target /`,
and remove the apps again with `sudo tool/macos_installer/uninstall.sh`.
`--skip-build` reuses the existing release builds.

## How Desktop and the Pin Code Manager talk

Loopback HTTP, chosen over a raw socket because it needs no extra packages, is
trivially debuggable with `curl`, never triggers a firewall prompt (loopback is
exempt on Windows), and matches how real eID connectors (Idemia Web Connector,
Web eID) integrate on a workstation.

1. Desktop binds `127.0.0.1:<ephemeral port>` (`PinReceiverServer`) and creates
   a random one-time bearer token and request id for this signing attempt.
2. Desktop launches the helper (`ProcessPinCodeManagerLauncher`):
   * macOS: through LaunchServices, `open -n -W -a "…/YesEm Pin Code Manager.app"
     --args --yesem-role=pincode --yesem-port=… --yesem-token=… --yesem-request=…`.
     `-W` keeps `open` alive until the helper quits, so Desktop notices a helper
     closed without a PIN.
   * Windows and Linux: `Process.start` on the helper executable (or on itself)
     with the same arguments, plus `YESEM_DESKTOP_*` environment variables.
3. The helper parses those arguments (`LaunchParameters`) and POSTs `PcmEvent`s
   to `/pcm/event` with `Authorization: Bearer <token>`: `opened` when its
   window is up, then `pinEntered` (with the PIN) or `cancelled`.
4. Desktop accepts only events carrying the current token and request id and
   invalidates the token on the first terminal event, so nothing can be
   replayed. The helper quits right after delivering.

### Where Desktop looks for the helper

In order (`PinCodeManagerLocator`), first match wins; `YESEM_PCM_APP` overrides everything:

* macOS: `<same Products dir>/<Mode>-pincode/YesEm Pin Code Manager.app`, then `/Applications`, `~/Applications`.
* Windows and Linux: the sibling `pincode/` folder produced by the bundle
  scripts, the sibling flavor build directory of Flutter 3.47+
  (`build/<os>/<arch>/pincode/…`), `yesem-pincode[.exe]` next to Desktop, then
  `%LOCALAPPDATA%\Programs\YesEm Pin Code Manager\`, `%ProgramFiles%\…` on
  Windows and `/opt/yesem/pincode/`, `/usr/local/bin/`, `~/.local/bin/` on Linux.
  Nothing found: Desktop runs its own executable in helper role.

Development tip: run the helper with `flutter run --flavor pincode` (or the
define), click Sign in Desktop, open its **Connection details** panel and paste
the port, token and request id into the helper's **Manual connection** form.

## Notes

* Showing the PIN in Desktop is for this test only. The PRD forbids displaying,
  storing or logging PINs in the real products.
* App Sandbox is disabled in `macos/Runner/*.entitlements`: the apps are
  distributed outside the App Store (ISAA) and Desktop spawns a helper process.
* macOS window titles and menus follow each flavor's product name automatically;
  the helper window is sized as a dialog in `MainFlutterWindow.swift`. On
  Windows and Linux the title comes from CMake when built with a flavor, and
  from Dart (`window_manager`) otherwise; the helper window is sized from Dart.
* The Windows and Linux runners were configured on macOS and have **not been
  compiled here**; the first build on those platforms is the real check.
  `tool/vm/UBUNTU_VM.md` walks through doing that on a VMware Fusion Ubuntu VM
  (`tool/vm/ubuntu_setup.sh` runs inside the guest, `tool/vm/ubuntu_from_mac.sh`
  pushes the project in from the Mac). `tool/vm/WINDOWS_VM.md` does the same for
  the Windows VM by running Claude Code inside it (`tool/vm/windows_bootstrap.ps1`).
